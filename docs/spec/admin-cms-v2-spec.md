# 運営CMS v2（公開前レビュー・手動記事化・フル構造エディタ） 製品仕様書

> 本書は既存プロダクト「LoL まとめ速報サイト自動運営システム」（[製品仕様](lol-matome-sokuhou-spec.md)）への **機能追加の差分仕様書** である。既存機能の再設計・置き換えは対象外で、明記した箇所だけを変更する。既存の技術ベースライン（`lol-matome-sokuhou-architecture.md`）は変更しない前提。

## 概要
自動運営で回っているまとめサイトに、運営者が「出すもの・出すタイミング・出す中身」を握れる編集機能を追加する。ゴールは次の4点である。

1. 運営者が任意の X 投稿／Reddit スレッドの URL を貼るだけで、盛り上がり判定（Hotness）を無視して強制的に記事の下書きを作れる。
2. 記事を原則「要レビュー」で止め、運営者が確認してから公開する。ただしカテゴリ単位で「自動公開」に切り替えられる。
3. 公開前に、記事の本文を**カテゴリごとの本文構造に合ったフル構造エディタ**（ブロックの追加・削除・並べ替え、各フィールドの編集）で直せる。
4. 公開後も同じエディタで直せ、保存すると公開サイトの一覧・詳細に即座に反映される。

現状は「moderation の保留（held）に引っかからない限り、パイプラインが生成した記事はすべて自動公開される」「編集画面は本文ブロック配列の生 JSON を textarea で書き換える粗い UI」という状態で、運営者が品質を担保する現実的な手段がない。本追加はその穴を埋める。

## 対象プラットフォーム
`web`（既存サイトと同一）。本追加で作る画面はすべて運営者向けの `/admin` 配下であり、既存の Basic 認証・非公開設定（`SITE_PRIVATE` 前提）・検索エンジン非インデックス（robots 除外）の内側に置く。一般閲覧者向けの公開サイト側の画面・導線は本追加では変更しない（唯一の観測可能な変化は「要レビュー状態の記事が公開サイトに一切現れないこと」と「公開後編集の内容が即時反映されること」）。

## ターゲットユーザー
- 本サイトの個人運営者（Basic 認証の資格情報を持つ唯一の運用者）。自動運営に任せつつ、目に付いた話題を自分の判断で記事化し、公開前に文言・構成を整えたい。
- 同運営者の「公開後に誤記・NG 表現・構成崩れを見つけて直したい」用途。

## スコープ外（Non-Goals）
- 公開サイト（閲覧者向け）のレイアウト・機能変更。本追加では公開サイト側の見た目を変えない。
- 5ch スレッドの手動記事化（対象は X 投稿 URL と Reddit スレッド URL のみ）。
- 複数運営者アカウント・ロール／権限管理・操作者ごとの監査ログ（運用者は Basic 認証の単一運営者を前提とする）。
- リッチテキスト（WYSIWYG）編集・自由 HTML 入力。編集はあくまで既存の構造化ブロックのフィールド編集にとどめる。
- 画像ファイルのアップロード基盤（画像ブロックは既存で許可されている URL／ローカル配信パスの指定のみを扱う）。
- 記事の版管理・世代ロールバック・編集差分の履歴閲覧。
- Hotness（盛り上がり判定）そのもののロジック変更・チューニング。手動記事化は「判定を通さない別経路」であって、判定式には触れない。
- AI 記事生成・タイトル生成・NG 言い換え等の生成品質の改修。手動記事化は既存の生成経路をそのまま使う。
- 記事の予約公開（scheduled）の仕様変更。既存の予約公開はそのまま残す。
- モバイル最適化された管理画面（`/admin` は PC ブラウザでの利用を主とする。横 1280px で崩れないことのみ担保する）。

## リスク・留意事項

- **X（旧 Twitter）API の利用規約・レート制限・コスト**: 手動記事化の X 経路は X の API 資格情報（`X_API_KEY` 相当）を必要とする。無料枠は取得件数が厳しく制限され、上位プランは有償である。よって（a）資格情報が未設定なら X 経路の入力欄と実行ボタンは「X の API キーが未設定のため利用できません」と明示して実行させない、（b）レート制限・認証失敗・対象投稿の削除／非公開は運営者に読める日本語メッセージで返し、記事を中途半端な状態で残さない、（c）1 回の操作で取得するのは指定された 1 投稿とその会話・引用の範囲にとどめ、無制限のクロールをしない。取得したポストの再掲は既存の引用方針（出典明記・逐語の扱い・NG 語処理）に従う。
- **Reddit の取得規約・レート制限**: Reddit 経路も既存の収集と同じく規約・レート制限の範囲で取得する。手動操作は運営者が連打しうるため、短時間の連続実行に対する抑制（実行中は再実行させない等）を設ける。
- **任意投稿の強制記事化に伴うコンテンツリスク**: 盛り上がり判定を通さないため、個人の小規模な投稿・炎上案件・特定個人への言及を含む投稿も記事化できてしまう。手動記事化で作られた記事も**既存の安全フィルタ（NG ワード・個人攻撃／晒し・出典欠落）を必ず通す**こととし、フィルタに引っかかった場合は公開せず保留（held）として理由を表示する。運営者がレビューで公開判断する経路と、フィルタが自動で止める経路の両方を残す。
- **URL パースの堅牢性**: 運営者が貼る URL は、モバイル共有リンク・短縮 URL・トラッキングパラメータ付き・`old.` などのサブドメイン違い・投稿への深いパーマリンク・末尾スラッシュ有無など多様である。対応しない形式は「この URL 形式には対応していません」と具体的に伝え、誤ったソースを取得して別の記事を作らない（無言で成功したふりをしない）ことを不変条件とする。ホワイトリストにないホストの URL は受け付けない。
- **「要レビュー」状態の後方互換**: 既存の記事状態は published / held / rejected / scheduled の 4 つで、公開サイトの閲覧系はすべて「published のみ」で絞り込んでいる。本追加では**記事状態をもう 1 つ（要レビュー）増やす必要がある**。既存 4 状態の意味・遷移・保留キューの表示を壊さないこと、既存記事（すべて既存 4 状態のいずれか）が本追加後も従来どおり表示・操作できることを必須条件とする。※状態の持ち方・列設計は実装側（architect/generator）の判断領域であり、本書では踏み込まない。
- **公開サイトに要レビュー記事を絶対に出さない不変条件**: 要レビュー状態の記事は、トップ一覧・カテゴリ一覧・タグ一覧・検索結果・アーカイブ・人気ランキング・関連記事・サイトマップ・RSS／フィード・個別記事 URL の直接アクセス・OGP／構造化データ出力を含め、公開側のあらゆる経路に一切現れてはならない。個別記事 URL を直接叩いた場合は公開記事と区別できない形（存在しない記事と同じ扱い）で拒否する。この不変条件は毎スプリントの受け入れ基準に含める。
- **既定を「全カテゴリ要レビュー」にすることによる更新停止リスク**: 本追加を入れた直後は、運営者が承認しない限り新規記事が 1 本も公開されなくなる。これは意図した仕様だが、運営者が気付かず更新が止まる事故を防ぐため、管理画面に「未レビュー件数」を目立つ形で常時表示し、現在どのカテゴリが自動公開／要レビューかを一目で確認できるようにする。

## 既存実装との差分整理

| 領域 | 既存（再利用する） | 本追加で新規に作る |
|---|---|---|
| 管理ダッシュボード | `/admin` の実行結果表・保留キュー・保留コメント・記事管理（編集リンク／ピン留め／予約解除）・公開記事総数・人気記事・失敗ログ | 公開ポリシー設定パネル、手動記事化パネル、レビューキュー、未レビュー件数バッジ |
| 承認操作 | 保留記事に対する「承認して公開」「却下」「予約公開に設定」の操作パターンと server action | 要レビュー記事に対する「承認して公開」「却下」「編集して公開」。保留（held）とは別カテゴリの状態として並存させる |
| 記事状態 | published / held / rejected / scheduled と、閲覧系の「published のみ」絞り込み | 要レビュー状態を 1 つ追加。パイプラインが公開ポリシーに従ってこの状態で保存する分岐 |
| 記事編集 | 編集ページの存在と保存経路、保存時の本文検証（`article-body.ts` のブロック検証） | タイトル＋本文生 JSON の textarea を廃し、ブロック単位の構造化エディタに置き換え。編集可能フィールドを要約・カテゴリ・タグ・サムネ・公開状態まで拡張 |
| 収集・生成 | 既存の収集アダプタ・記事生成・タイトル生成・安全フィルタ・カテゴリ判定 | URL 指定の単発取得経路と、盛り上がり判定を迂回して生成へ流す経路 |
| 公開反映 | オンデマンド再検証エンドポイント（機能 B の `/api/revalidate`） | 記事の編集保存・承認公開の完了時に、一覧と当該記事詳細の反映をトリガーする結線 |
| 記事本文の型 | `reaction` / `redditSource` / `heading` / `paragraph` / `quote` / `image` / `embed` / `linkButton` / `toc` / `patchChange` の各ブロック型と検証規則 | 各ブロック型に対応する編集 UI（型そのものは変更しない） |

## 用語の前提（既存仕様に合わせる）
- カテゴリの表示ラベルは既存定義に従う: 「5chの反応」「海外の反応」（Reddit 由来）「Xの反応」「パッチ/メタ」「Riot公式」「eスポーツ」。本書で「Reddit の反応」と述べる場合は既存ラベル「海外の反応」を指す。
- 「保留（held）」は安全フィルタ不通過による自動的な非公開であり、理由コードを伴う。本書の「要レビュー」は**フィルタは通ったが運営の確認待ち**という別の状態であり、両者を混同しない。

## 機能一覧

### F1. カテゴリ別 公開ポリシー設定（自動公開 / 要レビュー）
- 説明: 運営者が管理画面で、カテゴリごとに「自動公開」か「要レビュー」かをトグルで切り替えられる。設定は保存され、アプリを再起動しても保持される。既定値は全カテゴリ「要レビュー」。
- 既存との関係: 新規。既存にカテゴリ単位の公開ポリシーという概念は無い。
- 優先度: Must
- 受け入れ基準:
  - [ ] `/admin` に「公開ポリシー」パネルがあり、既存の全カテゴリ（5chの反応／海外の反応／Xの反応／パッチ/メタ／Riot公式／eスポーツ）が1行ずつ並び、各行に現在の設定（自動公開 or 要レビュー）が文字で表示される。
  - [ ] 設定が一度も保存されていない初期状態では、全カテゴリが「要レビュー」と表示される。
  - [ ] 任意のカテゴリのトグルを「自動公開」に切り替えて保存すると、画面の表示がそのカテゴリだけ「自動公開」に変わり、他カテゴリは「要レビュー」のまま変わらない。
  - [ ] ブラウザを再読み込みしても、直前に保存した設定がそのまま表示される。
  - [ ] アプリを停止・再起動した後に `/admin` を開いても、保存した設定が保持されている。
  - [ ] 「自動公開」に切り替えたカテゴリを再度「要レビュー」に戻せ、戻した結果が再読み込み後も保持される。
  - [ ] 未認証（Basic 認証を通さない）状態でポリシー変更の操作を直接実行しても、設定が変更されない。

### F2. 「要レビュー」記事状態とレビューキュー
- 説明: 記事に「要レビュー」という状態が加わり、その状態の記事は公開サイトに一切出ない。管理画面のレビューキューに一覧され、運営者は「承認して公開」「却下」「編集する」を選べる。
- 既存との関係: 状態の追加とレビューキュー UI は新規。承認／却下の操作パターン・ボタン配置は既存の保留キューを踏襲する。既存の held / rejected / scheduled / published の意味と挙動は変更しない。
- 優先度: Must
- 受け入れ基準:
  - [ ] `/admin` に「レビューキュー（要レビュー）」セクションがあり、要レビュー状態の記事がタイトル・カテゴリ・生成日時・出典リンク付きで新しい順に一覧表示される。
  - [ ] 要レビューの記事が0件のときは「要レビューの記事はありません」と表示され、エラーにならない。
  - [ ] レビューキューの記事に対し「承認して公開」を押すと、その記事が一覧から消え、公開サイトのトップ一覧に表示される。
  - [ ] レビューキューの記事に対し「却下」を押すと、その記事が一覧から消え、公開サイトのどこにも表示されない。
  - [ ] 要レビュー状態の記事は、トップ／カテゴリ一覧／タグ一覧／検索結果／アーカイブ／人気ランキング／関連記事／サイトマップのいずれにも現れない。
  - [ ] 要レビュー状態の記事の個別記事 URL に直接アクセスしても記事本文が表示されず、存在しない記事と同じ扱い（404 相当）になる。
  - [ ] 既存の「保留キュー」セクションは従来どおり別セクションとして表示され、保留記事が要レビューキューに混ざらない（逆も同様）。
  - [ ] 既存の保留記事に対する「承認して公開」「却下」「予約公開に設定」が従来どおり動作する。
  - [ ] レビューキューの件数が `/admin` 冒頭のバッジ（例: 「未レビュー 3件」）に表示され、承認・却下の後に件数が減る。

### F3. 自動収集パイプラインの公開ポリシー尊重
- 説明: 定期実行される自動収集パイプラインが記事を作るとき、その記事のカテゴリのポリシーを参照し、「自動公開」なら従来どおり公開、「要レビュー」なら公開せず要レビュー状態で保存する。安全フィルタで保留になる記事は従来どおり保留（ポリシーより優先）。
- 既存との関係: 新規の分岐。既存の収集・生成・安全フィルタ・重複排除の処理内容自体は変更しない。
- 優先度: Must
- 受け入れ基準:
  - [ ] 全カテゴリが「要レビュー」の状態でパイプラインを1回実行すると、公開記事は1件も増えず、生成された記事がすべてレビューキューに積まれる。
  - [ ] 特定カテゴリ（例: パッチ/メタ）だけを「自動公開」にしてパイプラインを実行すると、そのカテゴリの記事は公開記事として増え、他カテゴリの記事はレビューキューに積まれる。
  - [ ] 安全フィルタに引っかかる記事は、そのカテゴリが「自動公開」であっても公開されず、従来どおり保留キューに理由付きで入る。
  - [ ] パイプラインの実行ログ（既存の実行結果表）に、その実行で公開した件数・保留件数に加えて要レビューに回した件数が分かる形で記録される。
  - [ ] 予約公開（scheduled）に設定済みの記事は、本追加の後も予約時刻の到来で従来どおり公開される（要レビューに差し戻されない）。
  - [ ] ポリシー設定が一度も保存されていない状態でパイプラインを実行しても、エラーにならず全記事が要レビューになる（既定値が効く）。

### F4. 管理画面プレビュー（公開前の見た目確認）
- 説明: 要レビュー記事・公開前の下書きを、公開サイトの記事ページと同じ体裁（見出し・レス枠・強調色・埋め込みカード・パッチ表など）で `/admin` 配下から確認できる。運営者はプレビューを見てから承認・編集を判断する。
- 既存との関係: 新規。既存の記事本文レンダリングを管理画面から呼び出す形で、公開サイトの見た目と一致させる。
- 優先度: Must
- 受け入れ基準:
  - [ ] レビューキューの各記事に「プレビュー」導線があり、押すと `/admin` 配下のプレビュー画面が開く。
  - [ ] プレビュー画面に、記事タイトル・カテゴリ・タグ・サムネイル・本文の全ブロックが、公開記事ページと同じ構造（見出し／段落／引用／レス枠／埋め込みカード／パッチ変更表／目次）で表示される。
  - [ ] レス（reaction）ブロックの番号・名前・強調色・アンカーが、公開記事ページと同じ見え方で表示される。
  - [ ] プレビュー画面から「承認して公開」「編集する」「レビューキューに戻る」に遷移できる。
  - [ ] プレビュー画面は Basic 認証の内側にあり、認証なしでアクセスすると認証を要求される。
  - [ ] プレビュー画面は検索エンジンにインデックスさせない指定（robots 除外）を持つ。
  - [ ] プレビューを開いても、その記事が公開状態に変わらない（プレビュー後にレビューキューに残っている）。

### F5. 手動記事化: Reddit スレッド URL から下書きを作る
- 説明: 運営者が Reddit スレッドの URL を管理画面に貼って実行すると、そのスレッドとコメントを取得し、盛り上がり判定を無視して記事の下書き（要レビュー状態）を生成する。生成後はレビュー画面へ誘導する。
- 既存との関係: 新規の入力経路。取得後の記事生成・タイトル生成・カテゴリ付与・安全フィルタは既存の生成経路をそのまま使う。
- 優先度: Must
- 受け入れ基準:
  - [ ] `/admin` に「指定 URL から記事化」パネルがあり、URL 入力欄と実行ボタンがある。
  - [ ] Reddit のスレッド URL（`https://www.reddit.com/r/<sub>/comments/<id>/<slug>/` 形式）を入力して実行すると、処理中であることが画面に表示され、完了後に「記事を作成しました」という結果とその記事へのプレビュー／編集導線が表示される。
  - [ ] 作成された記事は要レビュー状態であり、公開サイトには表示されない。
  - [ ] 作成された記事のカテゴリが「海外の反応」になり、本文にスレッドの元投稿情報とコメント由来のレスブロックが含まれ、出典として元スレッド URL が保持される。
  - [ ] `old.reddit.com` のホスト違い、末尾スラッシュの有無、クエリパラメータ（`?utm_source=...` 等）付きの URL でも同じスレッドとして取得できる。
  - [ ] 盛り上がり（スコア・コメント数）が小さいスレッドの URL でも、判定で弾かれず記事が作成される。
  - [ ] 対応しないホスト（例: `https://example.com/...`）を入力すると「この URL 形式には対応していません」と表示され、記事は作成されない。
  - [ ] 存在しない／削除済みのスレッド URL を入力すると、その旨のエラーが表示され、中途半端な記事が作られない（レビューキューに空の記事が増えない）。
  - [ ] 既に同じスレッドから記事を作成済みの URL を再度入力すると、二重に記事が作られず「この URL は記事化済みです」と既存記事への導線が表示される。
  - [ ] 実行中は同じ操作を連続実行できない（ボタンが無効化される等、二重実行が発生しない）。

### F6. 手動記事化: X 投稿 URL から下書きを作る
- 説明: 運営者が X（旧 Twitter）の投稿 URL を貼って実行すると、その投稿と関連する返信・引用を取得し、盛り上がり判定を無視して記事の下書き（要レビュー状態）を生成する。X の API 資格情報が未設定の場合はその旨を明示し、実行させない。
- 既存との関係: 新規の入力経路。X 反応記事の本文構成（元ポスト埋め込み＋反応まとめ＋リプライ群）は既存のものを使う。
- 優先度: Must
- 受け入れ基準:
  - [ ] 「指定 URL から記事化」パネルで X の投稿 URL（`https://x.com/<user>/status/<id>` 形式）を入力して実行すると、完了後に「記事を作成しました」という結果とプレビュー／編集導線が表示される。
  - [ ] 作成された記事は要レビュー状態であり、公開サイトには表示されない。
  - [ ] 作成された記事のカテゴリが「Xの反応」になり、本文に元ポストの情報と返信／引用由来のレスブロックが含まれ、出典として元ポスト URL が保持される。
  - [ ] `twitter.com` ドメインの URL、クエリパラメータ（`?s=20` 等）付き URL でも同じ投稿として取得できる。
  - [ ] X の API 資格情報が未設定の環境では、X の URL を入力して実行しようとした時点で「X の API キーが未設定のため利用できません」と表示され、記事は作成されず、他の機能（Reddit 経路・レビュー・編集）は正常に使える。
  - [ ] 取得がレート制限・認証エラー・対象投稿の削除／非公開で失敗した場合、日本語のエラーメッセージが表示され、中途半端な記事が作られない。
  - [ ] 返信が1件も取得できなかった投稿でも、元ポスト単体の記事として下書きが作成される（空の記事にならない）。
  - [ ] 既に同じ投稿から記事を作成済みの URL を再度入力すると、二重に記事が作られず既存記事への導線が表示される。

### F7. フル構造エディタ 基盤（ブロック操作と記事メタフィールド）
- 説明: 記事編集画面を、本文ブロックを1件ずつカード状に並べて編集する構造化エディタに置き換える。ブロックの追加・削除・並べ替えができ、タイトル・要約（メタディスクリプション）・カテゴリ・タグ・サムネイル URL・公開状態も同じ画面で編集して保存できる。保存時は既存の本文検証を通し、不正なら保存せず理由を表示する。
- 既存との関係: 既存の編集ページ（タイトル＋本文生 JSON の textarea）を置き換える。保存時の本文検証規則は既存のものをそのまま使う。
- 優先度: Must
- 受け入れ基準:
  - [ ] 記事編集画面を開くと、本文の各ブロックが「ブロック種別のラベル付きカード」として上から順に並び、生の JSON テキストエリアは表示されない。
  - [ ] 各ブロックカードに「↑」「↓」の並べ替え操作があり、押すと表示順が入れ替わり、保存後に再度開いても入れ替えた順序が保持される。
  - [ ] 各ブロックカードに「削除」操作があり、削除して保存すると、そのブロックが記事から消える（プレビューにも公開ページにも現れない）。
  - [ ] 「ブロックを追加」操作からブロック種別を選べ、任意の位置（末尾および指定ブロックの直後）に新しいブロックを挿入できる。
  - [ ] タイトル・要約・カテゴリ（既存カテゴリからの選択）・タグ（複数、追加と削除）・サムネイル URL・公開状態を同じ画面で編集して保存でき、保存後に再度開くと編集内容が保持されている。
  - [ ] カテゴリを変更して保存すると、その記事が変更後のカテゴリ一覧に現れる（公開記事の場合）。
  - [ ] 本文が空（ブロック0件）になる編集を保存しようとすると保存が拒否され、「本文は1件以上のブロックが必要です」に相当するエラーが画面に表示され、記事は変更されない。
  - [ ] 検証に通らない値（例: 埋め込みブロックにホワイトリスト外の URL、レスブロックの本文行が空）を入力して保存すると、保存が拒否され、どのブロックのどのフィールドが不正かが分かるメッセージが表示され、入力内容が失われない。
  - [ ] 「キャンセル」で編集を破棄して一覧に戻れ、破棄した内容が記事に反映されていない。
  - [ ] 編集画面から「プレビュー」に遷移でき、保存済みの内容がプレビューに反映されている。

  - [ ] 反応記事のカテゴリでエディタを開いたとき、「ブロックを追加」の選択肢にその記事構成で使うブロック種別（レス／見出し／段落／引用／埋め込み／画像）が並ぶ。

### F9. パッチ系・その他ブロックのフィールド編集
- 説明: パッチ記事などで使われるブロック（パッチ変更、目次、画像、リンクボタン）の各フィールドを編集できる。パッチ変更ブロックは対象名・対象種別・方向（バフ／ナーフ／調整）・変更意図・スキル単位のグループと各変更行（数値変更／記述式変更）まで編集でき、グループと変更行の追加・削除ができる。

  - [ ] 再検証が設定不足などで実行できない環境でも、保存自体は成功し、その旨が管理画面に警告として表示される（保存が失われない）。

## 用語集
- **要レビュー**: 安全フィルタは通過したが、カテゴリの公開ポリシーにより運営者の承認を待っている記事の状態。公開サイトには一切表示されない。既存の「保留（held）」とは別の状態。
- **公開ポリシー**: カテゴリごとに設定する「自動公開」か「要レビュー」かの区分。自動収集パイプラインと手動記事化の双方が参照する（手動記事化は常に要レビューで作成する）。
- **レビューキュー**: 要レビュー状態の記事の一覧。運営者はここから承認・却下・編集・プレビューを行う。
- **手動記事化**: 運営者が指定した X 投稿 URL／Reddit スレッド URL から、盛り上がり判定を無視して記事の下書きを作る操作。
- **フル構造エディタ**: 記事本文を構造化ブロックのカードとして扱い、ブロックの追加・削除・並べ替えと各フィールドの編集を行う管理画面。生 JSON の直接編集を置き換える。
- **ブロック**: 記事本文を構成する単位（レス／Redditソース／見出し／段落／引用／画像／埋め込み／リンクボタン／目次／パッチ変更）。カテゴリによって使われる構成が異なる。
