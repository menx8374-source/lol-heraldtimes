# 成長G8 — Reddit収集の速報性向上（監視ベースの初速検出＋論争コメント取得）・純ルール

成長提案書(docs/growth-research.md G8・観点①②③)。Redditの話題を**より速く**拾う。**AI不使用（純ルール）**。対象: Web。

## 背景（実測に基づく設計・重要）
現状 `reddit.ts` は Arctic Shift の **2〜4日前の窓**（`DEFAULT_MIN_AGE_DAYS=2`/`DEFAULT_MAX_AGE_DAYS=4`）で取得し、収集時に `score >= minScore`（reddit=100）で足切りして上位を記事化候補にする。この2〜4日窓は**スコアのバックフィル遅延**を避けるための設計。

**実測（Arctic Shift, r/leagueoflegends, 今回検証済み）**:
- **直近0〜6時間の投稿は score 中央値=1・最大=1**（＝投稿直後はスコアがまだ反映されない＝バックフィル遅延は実在）。
- したがって**窓を単純に短縮すると逆効果**：新しい投稿は score=1 で `minScore` 足切りに全部落ち、記事化されない。
- `upvote_ratio` は全件取得できる（G1で使用中）。
- Arctic Shift の `sort=desc` は**時系列（新しい順）**で、スコア順取得はできない（クライアント側でscore降順ソート済み）。

**速報性を上げる正しい方向＝「収集の足切り」と「記事化の判定」を分離する**:
新しい投稿を**早期に監視対象（Post）として取り込み**、既存の `PostMetricsHistory` 監視（`fetchMetrics`）でスコア/コメントの伸びを追い、**既存 HotnessEvaluator の増加率（初速）判定**で「伸びている投稿」を最速で記事化する。score足切りは記事化ゲート（Hotness）で担保するため、収集段階で新規を捨てない。伸びなければ Hotness を満たさず記事化されない（ノイズは記事化段階で抑制）。

## 含まれる機能

### F-G8-1: 取得窓の前寄せ＋設定化（速報性）
- `reddit.ts` の取得窓 `DEFAULT_MIN_AGE_DAYS`/`DEFAULT_MAX_AGE_DAYS` を **env/config で上書き可能**にし（例 `REDDIT_MIN_AGE_HOURS`/`REDDIT_MAX_AGE_HOURS` の時間粒度、または既存の日粒度env）、**既定をやや前寄せ**する（例: min 2日→**約12時間**、max 4日→**約3日**）。これで「投稿後まもない伸び始めの投稿」も収集窓に入る。
- 窓の下限を前寄せしても、下記 F-G8-2 の「監視取り込み」と記事化ゲートで質を担保する。窓は純関数 `computeFetchWindow` の引数で受けており、境界はテストで固定できる形を維持する。

### F-G8-2: 監視のための足切り分離（収集で捨てない・記事化で絞る）
- 収集段階の `score >= minScore` 足切りを、**「新しい投稿（例: 収集時点で投稿から `REDDIT_MONITOR_MAX_AGE_HOURS`＝24時間以内）」には適用せず、Postとして保存し監視対象に入れる**よう変更する。古い投稿（監視ウィンドウ外）は従来どおり score 足切りを適用（バックフィルが効いており、伸びなかったものを今さら拾わない）。
- ただし**完全なノイズ抑制**として、新しい投稿にも最低限のフィルタは残す：既存のLoL関連キーワード一致（`isRelevantItem`/reddit許可サブレディット）に加え、`num_comments >= 1` 程度の「反応が始まっている」下限（＝bot投稿や無反応投稿の大量取り込みを避ける）。この下限は env で調整可能に。
- **記事化はあくまで既存 HotnessEvaluator に委ねる**（現在値 OR 増加率、G1論争度含む）。新規投稿はスコアが低くても、監視で `commentGrowthPerHour`/`scoreGrowthPerHour` が閾値を超えれば「初速が速い」として記事化される。伸びなければ記事化されない（既存の質ゲートがそのまま効く）。**post-pipeline / generate 側のロジックは変更不要**が理想（収集が監視対象を増やすだけ）。
- 監視対象が増えることによる Arctic Shift `fetchMetrics`（posts/ids）の呼び出し増は、既存のレート制御・監視上限（あれば）の範囲に収める。監視上限（同時に監視する Post 数の上限）が無ければ、暴走防止に上限を設ける（env 可）。

### F-G8-3: 論争/議論コメントの取得（記事の質・任意で軽量）
- コメント取得（`buildCommentsSearchUrl`/`fetchContent`）で、現状の score 降順上位に加え、**返信の多い（＝議論が起きている）コメント**も拾えるようにする（Arctic Shift が comment に `num_comments`/返信数を返すなら score とは別枠で数件確保）。返信数フィールドが無ければ、score上位のうち賛否が割れていそうなもの（既存データで取れる範囲）で代替し、**取得できなければ現状維持**（無理に増やさない）。
- これは「海外の反応」記事に賛否両論のコメントを含めて読み応えを増やすための軽量改善。**逐語維持・翻訳は既存経路**（G4）に合流。捏造しない。

## 制約・非目標
- **AIは使わない**（窓・足切り・監視・コメント選定はすべて純ルール/数値）。翻訳/SEO/生成の判定ロジックにAIを足さない。
- **記事化の質ゲート（Hotness）を弱めない**：収集で新規を取り込んでも、記事化は既存 Hotness（現在値 OR 増加率 OR 論争度）を満たしたものだけ。閾値を下げてノイズ記事を量産しない。
- **DBスキーマ変更なし**（既存 Post/PostMetricsHistory・sourceType・既存カラムを使う）。**新規npm依存なし**。
- 既存の 5ch/riot/riot-news/x ソースの挙動は不変。reddit の既存テスト（窓計算・足切り・変換）は、既定値変更に伴う調整はしてよいが、**純関数の境界テストは維持**する。
- Arctic Shift のバックフィル遅延という制約は消せない（実測済み）。本スプリントは「新規を監視で早期に捕捉し、伸びを最速で記事化する」ことで速報性を上げる（初回収集で確定スコアは得られない前提を尊重）。

## テスト（必須・実ネット非依存・実APIを叩かない）
1. `computeFetchWindow`（時間粒度化した場合含む）: env/引数で前寄せした窓の境界を検証。既定変更後も純関数の境界が正しい。
2. 足切り分離: 「新しい投稿（監視ウィンドウ内）」は score < minScore でも Post 保存対象に含まれ、「古い投稿」は従来どおり score 足切りされる。`num_comments>=1` 等の最低フィルタが効く。fetchはモック。
3. 監視上限: 監視対象が上限を超えない（暴走防止）。
4. 記事化の質ゲート不変: 監視取り込みされた低スコア新規投稿は、Hotness（増加率含む）を満たさない限り記事化されない（既存 evaluator ロジックが変わらないこと）。
5. 論争コメント取得: 返信数がある場合に議論コメントが数件含まれる。無い場合は現状維持で回帰しない。
6. 既存の reddit/収集/生成/パイプライン/hotness テストが回帰しない。

## 受け入れ基準
1. `npx vitest run` 全Green・`npx tsc --noEmit`・`npm run build`・`npm run lint` 通過。
2. 取得窓が前寄せされ、新しい投稿が監視対象（Post）として早期に取り込まれる。記事化は既存 Hotness（増加率＝初速・論争度含む）で判定され、伸びた投稿が従来より速く記事化される。
3. 収集で新規を取り込んでもノイズ記事が量産されない（記事化ゲートは Hotness のまま・閾値を下げない）。監視対象は上限で暴走しない。
4. AI不使用・DBスキーマ変更なし・新規依存なし・他ソース不変・記事化の質ゲート不変。

## 評価基準（evaluator向け）
- テスト全Green・build/tsc/lint通過・コンソールエラー0。
- 窓前寄せ・監視足切り分離・監視上限・記事化ゲート不変がテストで確認できる（実APIは叩かずfetchモック）。
- 速報性の改善（新規の早期監視取り込み）が、記事化の質（Hotnessゲート）を弱めずに実現されている。
- 受け入れ基準1〜4を満たす。
