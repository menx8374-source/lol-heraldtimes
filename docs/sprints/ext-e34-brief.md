# 拡張E34 — 公式パッチノートのまとめ記事を自動生成（パッチ/メタ）

運用フィードバック起点。対象: Web。参考体裁: lolninja.net（強化/弱体チャンピオン・アイテム、変更前⇒変更後）。

## 背景（なぜ）
- 現状の Riot 収集は「【パッチ】X のゲームデータが公開」という**汎用の事実速報**のみで、実際のパッチ内容（何が強化/弱体されたか）を伝えていない。
- 要望: パッチ/メタに**公式パッチノートのまとめ**を載せる。**捏造は厳禁**——LoL公式パッチノートの**実際の文面のみ**を要約する。
- リーク（PBE先行）は別ソースが必要なため本スプリント対象外（後日）。

## 含まれる機能

### F-E34-1: 公式パッチノートの取得
- `src/lib/collection/adapters/riot-datadragon.ts`（またはヘルパー新設）で、最新パッチの**公式パッチノートページ**（`buildPatchNoteUrl(version)`）を取得し、HTMLからテキストを抽出する `fetchPatchNotesText(version): Promise<string|null>` を追加。
  - `fetchTextSafe`（タイムアウト付き）でHTML取得 → 簡易にタグ除去＋HTMLエンティティ復号して本文テキスト化（新規npm依存は追加しない。正規表現ベースで可）。
  - 取得失敗・本文が短すぎる（例 数百字未満＝JSレンダリング等で本文が取れない）場合は **null**（例外を投げない）。
  - トークン節約のため、抽出テキストは上限（例 15000字）で切る。
- `buildPatchItem` は従来どおり sourceUrl=公式パッチノートURL・fetchedAt を保持しつつ、取得できた**パッチノート本文テキストを content に格納**する（取れなければ従来の汎用 content のまま）。パッチ検知は最新パッチのみ・dedupで重複回避（既存挙動維持）。

### F-E34-2: LLMによるパッチノート要約記事の生成
- riot（パッチ/メタ）の記事本文組み立て（`compose.ts`）で、content が**実パッチノート本文を含む**とき、LLM(Haiku)に要約させて「まとめ体裁」の本文ブロックを作る:
  - 見出し例: 「主な強化チャンピオン」「主な弱体チャンピオン」「アイテム・その他の変更」。各項目は**公式に書かれた変更のみ**、可能なら「変更前 ⇒ 変更後」で簡潔に。**本文に無い数値・調整を作らない**旨をsystem指示に明記（捏造防止）。
  - タイトルも「【パッチ】X.Y の主な変更点まとめ」等の分かりやすい形にする（E24のタイトル系を流用/簡易生成でよいが、パッチ番号は content/sourceから取る）。
  - LLMが使えない（GENERATION_MODE=mock・APIキー無し・APIエラー）／パッチ本文が無い場合は、**従来の汎用パッチ記事（簡易な事実速報）にフォールバック**（本体を止めない・記事は必ず出る）。
- 逐語転載の対象外（公式パッチノートは事実情報の要約。ただし長文丸コピーは避け、要点のまとめにする）。既存の出典（公式パッチノートURL）は必ず付ける。

## 制約・非目標
- **捏造禁止**: 公式パッチノートに実在する内容のみ要約。取得できないパッチは要約せず従来の簡易記事。
- リーク/PBEは対象外（別スプリント）。他ソース（reddit/5ch/clip）・タイトル(E24-26)・レス編集(E25/28/32/33)・NG(E27/29/30)・サムネ(E31)には触れない。
- 新規npm依存なし。LLM呼び出しはパッチ記事1本につき1回（新パッチ時のみ＝月2回程度・低コスト）。取得失敗・LLM不可は必ずフォールバック。
- 実パッチノートページがJSレンダリングで本文が取れない可能性がある（既知リスク）。その場合は null→従来記事にフォールバックし、後日ソース調整で対応する（本スプリントは「取れたら要約」まで）。

## テスト（必須・実API/実ネットワーク非依存）
1. `fetchPatchNotesText`: fetchをモックし、HTMLからテキスト抽出（タグ除去・エンティティ復号）。取得失敗/短すぎで null。上限で切る。
2. compose(riot): content が実パッチノート本文のとき、スタブLLMの要約が「まとめ体裁」本文になる（見出し＋要約）。出典URLが付く。
3. content が汎用（パッチ本文無し）または mock LLM／LLM例外のとき、従来の汎用パッチ記事にフォールバック（例外を投げない・記事は出る）。
4. 既存の riot 記事テスト・パイプラインテストが回帰しない（mock既定は従来挙動）。

## 受け入れ基準
1. `npx vitest run` 全Green（新規含む・実API/実ネット非依存）。
2. `npx tsc --noEmit`・`npm run build`・`npm run lint` 通過。
3. パッチノート本文が取得でき live LLM が使えるとき、パッチ/メタに「公式パッチノートのまとめ」記事が出る。取得不可/LLM不可なら従来の簡易パッチ記事にフォールバック（クラッシュしない）。
4. 捏造しない（公式文面のみ要約）。新規依存なし・コスト低（新パッチ時のみ）。

## 評価基準（evaluator向け）
- テストGreen・build/tsc/lint通過。実機(mock)でパッチ/メタ記事が従来どおり出る（回帰なし・コンソールエラー0）。
- スタブでパッチノート要約経路が動く（実ネット非依存）。
- 受け入れ基準1〜4を満たす。
