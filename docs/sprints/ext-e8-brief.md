# 拡張スプリント E8: コメントの返信スレッド＋賛否(Good/Bad)リアクション

対象プラットフォーム: web（Next.js App Router / SQLite+Prisma / Vitest。既存アーキテクチャに従う）

## 背景
拡張E2で匿名コメント（NGワードモデレーション付き）を実装済み。参考まとめサイト同様、
コメント同士のやり取り（返信）と、コメント・返信への賛否表明（👍/👎）を可能にする。

## 含まれる機能

### F-E8-1: コメントへの返信（1階層スレッド）
- 各コメントに「返信」ボタンを表示。押すとそのコメント宛の返信フォームが開く。
- 返信は親コメントに紐づけて保存し、公開画面では親コメントの直下にネスト（インデント）表示する。
- スレッドは**1階層**とする（返信への返信も、大元の親コメントにぶら下げる。多重ネストはしない）。
- 返信も既存コメントと同じ安全フィルタ（NGワード・個人中傷。`lib/moderation`）を通す。
  不通過は `status="held"` で記録のみ・公開画面に出さない（既存の不変条件を維持）。
- 返信本文もXSS対策（React子要素として描画・HTML解釈しない）。既存の `>>N` アンカー抽出も同様に扱う。
- 返信の投稿もコメント数（`Article.commentCount`）に加算する（公開された返信のみ）。

### F-E8-2: コメント・返信への賛否リアクション（👍 Good / 👎 Bad）
- 各コメント・各返信に「👍 数」「👎 数」ボタンを表示。押下でカウントを加算し即時反映する。
- ログイン無し方針のため、ユーザー単位の多重投票防止はせず、UI側の連打抑止（楽観更新・二重送信防止）で足りる仕様とする（既存の記事絵文字リアクション `lib/reactions` / `reaction-buttons` と同じ思想）。
- カウントは永続化し、リロード後も保持される。

## データモデル変更（要マイグレーション）
- `ArticleComment` に以下を追加:
  - `parentId String?`（自己リレーション。返信の場合に親コメントIDを持つ。トップレベルは null）
  - `goodCount Int @default(0)` / `badCount Int @default(0)`
  - 自己リレーション（`parent`/`replies`）と必要なindex（例: `@@index([articleId, parentId])`）。
- 既存の `@@unique([articleId, number])`（記事内表示連番）は維持する。返信にも記事内で一意な `number` を振ってよい（アンカー参照との整合）。
- マイグレーション名は `add_comment_reply_and_votes_e8` 等わかりやすく。既存データ（親なしの既存コメント）は parentId=null・カウント0で移行できること。

## 実装方針
- 投稿・投票は Server Action（既存 `comment-section` の投稿フローに倣う）。公開限定・held維持の不変条件を壊さない。
- 投票 Server Action は対象コメントIDと種別(good/bad)を受け取り、`increment` で加算。存在しない/held コメントには加算しない。
- コメント取得（`lib/comments-db`）を、トップレベルコメント＋その公開返信をまとめて返す形に拡張する（N+1を避け、記事単位で1〜2クエリにまとめる）。
- シード（`prisma/seed.ts`）に、返信付きコメント・Good/Bad初期値のサンプルを最低1記事追加し、実機で見える状態にする（すべてオリジナル創作テキスト）。

## 受け入れ基準（検証可能・原文）
- [ ] 公開記事のコメントに「返信」ボタンがあり、押すと返信フォームが開く。
- [ ] 正常な返信を投稿すると、対象コメントの直下にインデント表示され、コメント数が加算される。
- [ ] NGワード/個人中傷を含む返信は公開されず（held）、公開画面に一切表示されない。
- [ ] 返信本文に `<script>` 等を入れてもエスケープされ、スクリプトとして実行されない。
- [ ] 各コメント・各返信に 👍/👎 ボタンと現在数が表示され、押すと数が1増えて即時反映される。
- [ ] リロード後も 👍/👎 の数・返信が保持される（永続化されている）。
- [ ] 返信・投票を経ても、保留(held)コメントや held/scheduled/rejected 記事が公開画面に露出しない。
- [ ] `npm test` が全てGreen（返信のモデレーション・投票加算・取得整形のロジックに最小限のテストを追加）。

## 評価基準（evaluator向け）
- 致命的バグ0件／コンソール・実行エラー0件／上記受け入れ基準の充足率100%／テストGreen。1つでも下回れば全体FAIL。
- 検証は Playwright MCP で実機操作（返信投稿・👍/👎押下・リロード後の保持・NGワード返信のhold）で行う。
