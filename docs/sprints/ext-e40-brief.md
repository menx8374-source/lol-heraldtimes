# 拡張E40 — パッチ記事の捏造タイトル解消＋変更点の決定的（逐語）抽出

運用フィードバック起点（重大: 誤情報）。対象: Web。

## 背景（なぜ・現象）
実機のパッチ記事が次の2つの問題を起こした:
1. **タイトル捏造**: 「【速報】パッチ26.14はT1三連覇記念版、複数チャンピオン調整とシーズン3へ移行」。
   「T1三連覇」は公式パッチノート冒頭に実在するが、「シーズン3へ移行」は本文に無く**捏造**。
   原因: パッチ記事にも煽りタイトルLLM（`generateHookTitleLLM`）を使っており、拡張E26で「本文由来の
   具体要素を含む」チェックを撤廃したため、ラベル＋文字数さえ満たせば**事実に無い主張でも通ってしまう**。
   パッチノートは事実性が最優先で、煽り編集タイトルは不適切。
2. **本文が要約できずクリーンフォールバック**: 「自動要約では正確に抽出できなかった」定型文になっていた。
   検証の結果、**公式ページからは変更点（例「アジール」「コーキ 基本ステータス レベルアップごとの攻撃力: 2 ⇒ 2.5」
   「ガレン R - デマーシアの正義 確定ダメージ: 150/250/350 ⇒ …」）が十分に取得できている**（本文は問題なく取れている）。
   それでも `composePatchSummaryBody`（LLM要約）が空を返し、クリーンフォールバックに落ちていた。
   → LLM要約に依存せず、本文から**「⇒」を含む変更行を決定的・逐語で抽出**すれば実用的な本文が作れる。

## 含まれる機能

### F-E40-1: パッチ記事（riot）のタイトルを事実ベースにする（煽りLLMを使わない）
- `src/lib/generation/generate-article.ts` のタイトル決定で、**`sourceType === "riot"` のときは
  `generateHookTitleLLM` を呼ばず、事実タイトル（`candidate.title`）をそのまま使う**。
  （`buildPatchItem` が既に「【パッチ】26.14 の主な変更点まとめ」を生成しているため、それを採用＝捏造の余地なし。）
- 反応記事（5ch/reddit）・clip は従来どおり `generateHookTitleLLM`（惹きつけタイトル）を使う（変更しない）。
- ※任意（過剰実装しない）: パッチ番号に加え、F-E40-2 の決定的抽出で検出した**主要チャンピオン名（逐語）**を
  タイトル末尾に足して「【パッチ】26.14 主な調整まとめ｜アジール・コーキ・ガレン 他」のようにしてもよい。
  ただし本文に無い語・編集的な主張（「記念版」「移行」等）は一切加えない（捏造禁止）。実装が煩雑なら番号のみでよい。

### F-E40-2: 変更点の決定的（逐語）抽出フォールバック（compose.ts）
- riot かつ content が実パッチノート本文（`content.length >= PATCH_NOTES_MIN_LENGTH`）のとき、
  本文から**チャンピオン別の変更点を決定的に抽出**する純関数を追加する（例 `extractPatchChangesDeterministic(text)`）。
  - **チャンピオン節の検出**: 単独行がチャンピオン名（日本語表記）と一致する行を節の開始とみなす。
    チャンピオン名リストは既存のものを再利用する（`title.ts` の `CHAMPIONS` を `export` して使う、
    もしくは同等の純粋な日本語チャンピオン名リスト。http依存モジュールは import しない）。
  - **変更行の抽出**: 各チャンピオン節内で、値変更マーカー **「⇒」を含む行**（例「攻撃力: 2 ⇒ 2.5」）を
    そのチャンピオンの変更点として**逐語で**集める（本文の部分文字列のみ。数値やスキル名を作らない＝捏造禁止）。
    直前の非空行（スキル名/項目名。例「基本ステータス」「R - デマーシアの正義」）を文脈として前置してよいが、
    無ければ変更行のみでよい。
  - **有界化**: チャンピオン最大 ~12 体、1体あたり変更行最大 ~5 行程度に制限（読みやすさ・トークン節約）。
  - 変更点が1件も取れなければ null を返す。
- `composeArticleBody`（riot 分岐）のフォールバック順を **3段**にする:
  1. `composePatchSummaryBody`（LLM要約）が blocks を返せばそれ（従来。LLMが使える時の綺麗なまとめ）。
  2. 返さなければ `extractPatchChangesDeterministic` の結果から本文ブロックを組む
     （見出し「主な変更点（公式パッチノートより）」＋チャンピオンごとの段落。逐語）。1件以上あればこれを採用。
  3. それも空なら従来の `composeCleanPatchFallbackBody`（クリーン定型）。
- 可観測性: 決定的抽出で検出したチャンピオン数を `console.log`（例 `[patch] deterministic changes champions=8`）。
  0件時は本文が取れていない可能性の切り分けになる。

## 制約・非目標
- **捏造禁止**（本文に実在する変更・チャンピオン名のみ。逐語抽出は本文の部分文字列だけを使う）。
- 反応記事/clipのタイトル・本文、NG・強調色・サムネ・5ch収集には触れない。新規npm依存なし。
- mock既定（APIキー無し）ではパッチノート本文取得は走らず従来どおり（回帰なし・コスト0）。LLM呼び出しは増やさない
  （決定的抽出はLLM不使用）。
- リーク/PBEは対象外。

## テスト（必須・実API/実ネット非依存）
1. F-E40-1: riot 候補（candidate.title="【パッチ】26.14 の主な変更点まとめ"）の生成記事タイトルが
   **candidate.title と一致**し、`generateHookTitleLLM` を経由しない（煽りフック・捏造が入らない）。
   反応(5ch/reddit)候補のタイトルは従来どおり `generateHookTitleLLM` 経由（回帰なし）。
2. F-E40-2 抽出（純関数）: 実パッチノート相当のテキスト（チャンピオン名行＋「⇒」変更行を含む fixture）から、
   チャンピオン別の変更点が**逐語で**抽出される（本文の部分文字列であること・チャンピオン数/行数の上限が効くこと）。
   「⇒」を含まないノイズ（intro/クレジット/TFT導線）は拾わない。変更行ゼロなら null。
3. compose 分岐: content が実本文で LLM要約が null（スタブ）でも、**決定的抽出で変更点があれば
   「主な変更点」本文**になり、クリーン定型には落ちない。決定的抽出も空なら従来のクリーン定型。
   LLM要約が成功すれば従来どおりそれを優先（回帰なし）。
4. 既存の compose/patch/title/generate-article テストが本仕様に沿って回帰しない（riotタイトルの期待を更新）。

## 受け入れ基準
1. `npx vitest run` 全Green（新規/更新含む・実API/実ネット非依存）。
2. `npx tsc --noEmit`・`npm run build`・`npm run lint` 通過。
3. パッチ記事のタイトルが事実ベース（捏造・煽りが入らない）。本文は、変更点が本文にあれば
   チャンピオン別の逐語変更点まとめになり、取れないときのみクリーン定型。捏造なし。
4. 逐語維持・新規依存なし・LLM呼び出し増なし・mock既定は回帰なし。

## 評価基準（evaluator向け）
- テストGreen・build/tsc/lint通過。mock/生成パイプラインが回帰しない（コンソールエラー0）。
- riotタイトルが事実ベースであること、決定的抽出が逐語で変更点を出すこと、3段フォールバックの分岐が
  テスト/データで確認できる。
- 受け入れ基準1〜4を満たす。
