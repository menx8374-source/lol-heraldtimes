# パッチ刷新S6 — パッチノートの全構造パターンに対応（パーサ堅牢化・実データ5パッチ検証）

ユーザー報告の不具合（アジールWの変更内容が空・システム以下の項目が崩れる）を、**過去5パッチ（26.10〜26.14）の実HTMLで構造を網羅分析**した結果に基づき根治する。
現状パーサ（S1）は「h3対象名＋h4スキルキー＋`li内 ⇒` 数値変更」だけを前提にしており、実際のパッチノートの多様な構造に対応できていない。**AI不使用**。対象: Web。

## 背景（実データ5パッチで判明した未対応パターン）
分析対象: `src/lib/generation/__fixtures__/patches/patch-{2614,26-13,26-12,26-11,26-10}.html`（本番実HTML。**generatorは必ずこれらを読んで全パターンを把握**すること）。判明した現状パーサの欠陥:

1. **⇒（矢印）を含まない「記述式変更」が大量**（26.12は数値変更88件に対し記述式150件と逆転）。現状は `li` に `⇒` が無いと変更を取れず**丸ごと欠落**する。
   - 例（アジールW・26.14）: 「征服者が通常攻撃時に1ではなく2スタックを適用するようになりました」「プレスアタックが最初に命中した対象に適用されるようになりました」← これらが表示されず「Wの中身が空」になっていた。
   - 例（バグ修正）: 「ケイトリンのヘッドショットが茂みの中から発射されないことがあった不具合を修正しました」。
2. **h3（対象名）が無いブロックが毎パッチ9〜11個**（システム/アリーナ/バグ修正/オーグメント等）。現状はh3が無いと対象を確定できず、h4を誤ってスキル扱いし前後が混線する（例: システム「ブルーバフ」がh3無し・h4開始）。
3. **`patch-change-block` ですらないブロック**（`<div class="white-stone">` 直下）。バグ修正セクション等はこの構造で、h3/h4無し・blockquote＋ul。
4. **h4見出しの多様性**: `Q/W/E/R/固有スキル/パッシブ/基本ステータス`（スキルキー）以外に、「オーグメント」「システムの変更」「アイテムのバランス調整」「Q1 - 巻雲」「近接ミッドのロールクエスト」等の**小見出し・対象名・カテゴリ**が来る。スキルキーでないh4を誤ってスキル扱いしていた。
5. **複数の意図文（blockquote）**やブロック内のネスト（意図→変更→再び意図→変更）。
6. **セクション種別が豊富**: チャンピオン/アイテム/システム/アリーナ/ルーン/ランダムミッド/バグ修正＆QoLの変更/エッセンスストア/各種システム見出し 等。

## 一般化した構造モデル（これに沿ってパースする）
```
<h2 id="patch-*">セクション名</h2>
  <div class="content-border"><div class="(patch-change-block|white-stone) ...">
     ├ <img>（対象アイコン, 任意）
     ├ <h3 class="change-title">対象名</h3>（任意・無い場合あり）
     ├ <blockquote>意図</blockquote>（0個以上・複数可）
     ├ <ul><li>…</li></ul>（h4が無いとき＝対象直属の変更）
     └ <h4 class="change-detail-title">見出し</h4>（0個以上）
          └ <ul><li>変更</li></ul>
   li の中身は2種:
     (a) 数値変更: <strong>stat</strong>：before ⇒ <strong>after</strong>
     (b) 記述式変更(⇒なし): <strong>ラベル</strong>：説明文 / または説明文のみ
```

### 決定ルール（誤帰属ゼロ・逐語維持）
- **対象名**: ① `h3.change-title` があればそれ。② 無ければブロック先頭の非スキルh4のテキスト。③ それも無ければ直近の `h2` セクション名（例: バグ修正のwhite-stoneブロック→対象名「バグ修正＆QoLの変更」）。
- **対象ID/kind**: 対象アイコンURLのファイル名から（champion/item）。無ければセクション名からkind推定（システム/アリーナ/バグ修正/ルーン/オーグメント/other）。
- **グループ(h4)**: h4テキストの先頭が `パッシブ/固有スキル/基本ステータス/[QWER]([ -－].*)?` に一致→スキルグループ（abilityKey判定）。一致しないh4→**小見出しグループ**（abilityKeyなし・見出しは表示するが色分けしない）。h4が無い→対象直属グループ（見出しなし）。
- **変更(li)**:
  - `⇒` を含む→数値変更（stat=先頭strong、before=「：」と「⇒」の間、after=⇒以降のstrong/テキスト）。
  - `⇒` を含まない→**記述式変更**（先頭strongがあれば `label`＋`text`、無ければ `text` のみ。**本文を逐語でそのまま保持**。数値を作らない）。
- **意図**: blockquoteは全て拾い、対象の意図として結合（複数可）。
- **ノイズ除外**: リンク集/TFT導線/画像onlyのpは変更にしない。

## 含まれる機能

### F-S6-1: パーサ堅牢化（patch-notes-parser.ts）
上記モデルに従い `parsePatchNotesHtml` を再設計（S1の型は活かしつつ、h3無し・非pcbブロック・多様なh4・記述式liに対応）。5パッチすべてで対象・グループ・変更が正しく紐づき、誤帰属ゼロ・欠落ゼロにする。

### F-S6-2: 記述式変更に対応する型（article-body.ts / パーサ型）
`PatchChange` を数値変更と記述式変更の両対応にする（後方互換）:
```ts
type PatchChange = { stat?: string; before?: string; after?: string; text?: string };
// 数値変更: stat/before/after を持つ。 記述式変更: text（＋任意でstat=ラベル）を持つ。
```
`ArticleBodyPatchChangeGroup.changes` も同型。`parsePatchChangeBlock` 検証を更新（逐語・改変なし）。

### F-S6-3: compose / direction（記述式考慮）
- `composeDetailedPatchBody`（DOM経路）が上記の全対象・全グループ・全変更（数値＋記述式）を patchChangeブロックに反映。
- `direction` 算出は**数値変更(⇒あり)からのみ**判定（既存 classifyPatchChange）。記述式のみのグループ/対象は数値が無いので **adjust**（安全側・既存方針どおり）。
- 冒頭サマリの体数集計・目次・3グループ振り分けは維持。アイテム/システム/アリーナ/バグ修正/オーグメント等の非チャンピオン対象は、各セクションに**対象名付きカード**で出す（総称に潰さない）。

### F-S6-4: 記述式変更の表示（article-body-view.tsx）
- patchChangeブロックのレンダリングで、記述式変更（`text`）を表示する: `label：text`（labelあり）または `text`（labelのみ）。**S4のLoLダーク意匠を踏襲**（金/紺）。記述式は before⇒after の色分けをせず中立表示（金or本文色）。数値変更は従来どおり before(グレー)⇒after(direction色)。
- 見出しの無いグループ・小見出しグループも自然に表示（崩れない）。

## 制約・非目標
- **AIは使わない**（純粋なDOMパース/表示）。**逐語維持・捏造禁止**（記述式変更も本文の文章をそのまま。要約・数値化しない）。
- 反応記事/翻訳/SEO/他ソース・fact/summaryモードは不変。DOM失敗時は既存の平テキスト→事実速報にフォールバック（temp）。
- **フル5パッチHTML（`__fixtures__/patches/`）はコミットしない**（各300KB前後で重い）。generatorはこれらを分析に使い、**各パッチから構造の多様性を代表するブロックを抜粋した軽量フィクスチャ**を `__fixtures__/` に作成してテストに使う（アジールW=記述式・システムのh3無し・バグ修正のwhite-stone・オーグメントのh4小見出し・アイテム・数値/記述式両方 を必ず含む）。作業後 `__fixtures__/patches/` ディレクトリは削除する。
- DBスキーマ変更なし・新規npm依存なし（既存の正規表現/限定パース方針を継続。堅牢性のため軽量HTMLパーサを足す場合は npm audit でCritical/High無しを確認）。

## テスト（必須・実データ抜粋フィクスチャ・実ネット非依存）
1. **アジールW（記述式3項目）が表示される**（26.14）: W見出し配下に「征服者が…2スタック」等3件が逐語で出る。空でない。
2. **誤帰属ゼロ維持**: アジール=W/R、コーキ=基本ステータス(2⇒2.5)/R。
3. **h3無しブロック**（システムのブルーバフ）: 対象名「ブルーバフ」で、`スキルヘイスト：10 ⇒ 10/15/20` が出る。h4を対象名として正しく扱う。
4. **white-stoneブロック**（バグ修正＆QoL）: 対象名がセクション名等で、記述式の箇条書き（「ケイトリンのヘッドショット…修正」等）が逐語で出る。前のブロックに吸い込まれない。
5. **多様なh4**（オーグメント/カテゴリ小見出し/Q1 - 巻雲 等）: スキルキー判定に該当しないh4が小見出しとして表示され、スキル誤認しない。
6. **記述式変更のdirection**: 記述式のみのグループ/対象は adjust。数値変更を含む対象は既存どおり分類。
7. 5パッチ抜粋フィクスチャで、対象・グループ・変更の欠落ゼロ・誤帰属ゼロ・逐語一致を検証。既存の parser/compose/article-body-view/seo/search テストが回帰しない。

## 受け入れ基準
1. `npx vitest run` 全Green・`npx tsc --noEmit`・`npm run build`・`npm run lint` 通過。
2. アジールWの変更内容・システム/アリーナ/バグ修正/オーグメント/アイテムの各対象と変更が、**対象名・スキルキー/小見出し・変更内容（数値＋記述式）付きで正しく**表示される（ユーザー報告の②③解消）。誤帰属ゼロ・欠落ゼロ・逐語維持。
3. 記述式変更はadjust/中立表示、数値変更は色分け。S4デザイン踏襲。AI不使用・DBスキーマ変更なし・新規依存なし。フル5パッチHTMLはコミットしない。

- アジールWが埋まり、システム以下が正しい対象/内容で出る。逐語維持。S4意匠が保たれる。
