# admincms-S5 — 公開後編集の即時反映とレビュー運用の仕上げ

仕様書 `docs/spec/admin-cms-v2-spec.md` の **Sprint 5**（F10, F11）を実装する。運営CMS v2の最終スプリント。公開後の編集を公開サイトへ即時反映し、レビューキューの運用（カテゴリ絞込・一括承認）を仕上げる。

## 前提（S1〜S4で実装済み・利用する）
- レビューキュー・承認/却下・プレビュー（S1）／手動記事化（S2）／フル構造エディタ（S3・S4、全10ブロック型編集可）。
- `updateArticleContent`（`src/lib/admin/articles-admin.ts`）＝編集保存＋moderation再チェック＋published降格不変条件。`updateArticleAction`（`src/app/admin/actions.ts`）＝useActionStateでエラー返却。
- 承認 `approveReviewArticle` は既に `revalidatePublishedListings`（機能B `/api/revalidate`、`src/lib/generation/revalidate-listings.ts`）を呼ぶ。編集保存側(`updateArticleAction`)は現状 `revalidatePath("/admin")`＋`revalidatePath("/")` のみ。

## 含まれる機能（F10, F11・要点）
- **F10 公開後編集の即時反映**: 公開済み記事を編集保存すると、再ビルドなしで公開サイトの**トップ一覧のカード見出し・個別記事詳細・カテゴリ一覧・タグ一覧**に即反映。承認公開も即トップに出現。公開済み→「要レビュー」に戻す編集をすると公開サイト（一覧・詳細・個別URL=404相当）から消えレビューキューに現れる。検証エラーで保存失敗時は公開内容が一切変わらない。再検証が設定不足で実行できない環境でも**保存自体は成功し管理画面に警告表示**（保存は失われない）。
- **F11 レビュー運用効率化**: レビューキューのカテゴリ絞込フィルタ、チェックボックスでの複数選択→「選択した記事をまとめて承認」、まとめて承認の結果（成功/失敗件数＋失敗理由）表示、記事管理一覧に「要レビュー」ラベル、0件時の表示。

## 受け入れ基準（仕様書 Sprint 5 原文）
- [ ] 公開済み記事の編集画面でタイトルを変更して保存すると、再ビルド・再起動なしに、公開サイトのトップ一覧の当該記事カードの見出しが新しいタイトルに変わる（保存直後にトップを開いて確認できる）。
- [ ] 同じ変更が、その記事の個別記事ページ（詳細）でも保存直後に反映されている。
- [ ] 公開済み記事に段落ブロックを1件追加して保存すると、個別記事ページにその段落が保存直後に表示される。ブロックを削除して保存すると、保存直後に消える。
- [ ] 公開済み記事のカテゴリを別カテゴリに変更して保存すると、変更前カテゴリの一覧から消え、変更後カテゴリの一覧に現れる（両方の一覧を開いて確認できる）。
- [ ] 公開済み記事にタグを1つ追加して保存すると、そのタグの一覧ページにその記事が現れる。
- [ ] レビューキューの記事を「承認して公開」した直後に公開サイトのトップを開くと、その記事が一覧に現れる。
- [ ] 公開済み記事を編集画面で公開状態「要レビュー」に変更して保存すると、保存直後に公開サイトのトップ一覧・カテゴリ一覧・個別記事ページから消え（個別 URL は 404 相当になり）、レビューキューに現れる。
- [ ] 検証エラーで保存が失敗したとき、公開サイトの当該記事の内容が一切変わらない（部分的に壊れた記事が公開されない）。
- [ ] 再検証が設定不足で実行できない環境でも、保存自体は成功して管理画面に「一覧への即時反映ができませんでした」に相当する警告が表示され、編集内容は失われない。
- [ ] レビューキューにカテゴリ絞り込みのフィルタがあり、カテゴリを選ぶとそのカテゴリの記事だけが一覧され、「すべて」に戻すと全件が一覧される。
- [ ] レビューキューの各記事にチェックボックスがあり、3件中2件を選択して「選択した記事をまとめて承認」を実行すると、選択した2件だけが公開サイトのトップ一覧に現れ、選択しなかった1件はレビューキューに残る。
- [ ] まとめて承認の実行後、結果（成功件数・失敗件数と失敗理由）が画面に表示され、未レビュー件数バッジが承認した件数分だけ減る。
- [ ] 1件も選択せずに「まとめて承認」を実行しても、エラーにならず「記事が選択されていません」に相当する案内が表示され、記事状態が変わらない。
- [ ] レビューキューが0件になったとき「要レビューの記事はありません」「未レビュー 0件」と表示され、フィルタやまとめて承認の操作でエラーにならない。
- [ ] S1〜S4 の全機能（公開ポリシー設定、パイプラインのポリシー尊重、手動記事化、プレビュー、フル構造エディタ）が本スプリントの変更後も従来どおり動作する。
- [ ] 全スプリントを通した不変条件として、要レビュー状態の記事が公開サイトの一覧・カテゴリ・タグ・検索・アーカイブ・ランキング・関連記事・サイトマップ・個別記事 URL のいずれにも現れないことを、要レビュー記事が存在する状態で改めて確認できる。

## テスト観点（自動テストを書く対象・原文）
- 反映トリガーの条件: 記事の保存・承認公開・要レビューへの差し戻しで反映処理が呼ばれること、保存が検証エラーで失敗したときは呼ばれないこと。
- 反映失敗時の扱い: 反映処理が失敗しても保存結果が保持され、警告として扱われること（保存が巻き戻らないこと）。
- まとめて承認: 選択件数0件、一部が失敗するケース、全件成功のそれぞれで、成功／失敗の集計と記事状態が期待どおりになること。
- 絞り込み: カテゴリ指定時に対象カテゴリの要レビュー記事のみが返り、他状態（公開・保留・却下・予約）の記事が混ざらないこと。

## 実装ガイド（既存コード結線・オーケストレーターより）
- **公開後編集の即時反映（F10）**: `updateArticleAction`（成功時）で、既存 `revalidatePublishedListings`（機能B・全固定一覧パスを再検証）＋**当該記事の個別詳細パス**を `revalidatePath` する。カテゴリ変更・タグ変更・review⇄published遷移でも一覧/詳細が正しく更新されるように、記事のslug（詳細URL）を保存後に取得して再検証。承認(`approveReviewArticle`)は既に機能Bを呼ぶので踏襲。
  - **反映失敗の扱い**: `revalidatePublishedListings` はネットワーク/設定不足で失敗し得る（REVALIDATE_SECRET未設定時はno-op、URL到達不可時は例外）。**保存(DB更新)は既に確定しているので巻き戻さず**、再検証の失敗を握って `updateArticleAction` の戻り値に警告フラグ（例 `{success:true, revalidateWarning:true}`）を載せ、エディタ(useActionState)が「一覧への即時反映ができませんでした（保存は完了）」相当の警告を表示する。保存は失われない。純関数として「保存は成功・再検証は任意」を切り分ける。
- **レビュー運用効率化（F11）**:
  - **カテゴリ絞込**: `listReviewQueue({ category? })` に絞込を足す（未指定=全件）。`/admin` のレビューキューにカテゴリselect（「すべて」＋6カテゴリ）。
  - **一括承認**: server action `bulkApproveReviewArticlesAction`（articleIdの配列を受け、各を `approveReviewArticle` で承認）。結果 `{ succeeded, failed:[{id,reason}] }` を集計して返し表示。0件選択は「記事が選択されていません」案内で状態不変。レビューキューUIにチェックボックス＋「選択した記事をまとめて承認」。一括承認後も機能Bで一覧即反映。
  - **記事管理ラベル**: 既にS1で「要レビュー」ラベルは追加済み（`ARTICLE_STATUS_LABELS`）。0件時表示・バッジ更新の整合を確認。
- **不変条件の再確認**: 公開後編集で review に戻した記事・一括承認で残った未選択記事が、公開側の全経路（一覧/カテゴリ/タグ/検索/アーカイブ/ランキング/関連/sitemap/個別URL404）に出ないこと。

## 制約・非目標
- 公開サイトの見た目・導線は変更しない（反映の仕組みのみ）。ブロック型・article-body.ts・表示コンポーネントは不変。S1の「要レビュー記事が公開側に出ない不変条件」を壊さない。
- 機能B(`/api/revalidate`)の既存の認証(REVALIDATE_SECRET)・除外設定は変更しない。予約公開(scheduled)の仕様も不変。
- 新規依存は最小限。テスト必須（上記テスト観点：反映トリガー条件・反映失敗時の保存保持・一括承認の集計と状態遷移・カテゴリ絞込）。横1280pxで崩れない。
- これがv2最終スプリント。完了till後、全体の受け入れ基準（要レビュー記事の公開側非表示の不変条件）を通しで再確認する。
