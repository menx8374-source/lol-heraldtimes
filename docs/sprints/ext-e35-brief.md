# 拡張E35 — 公式パッチノート要約の品質修正（ノイズ除去・失敗時のクリーンフォールバック）

E34/E34cの続き。取得は成功しているが要約が破綻していた問題を直す。対象: Web。

## 背景（なぜ・現象）
- E34cでURLを直し、公式パッチノート本文の取得自体は成功（実際の26.14内容が取れている）。
- しかしパッチ/メタ記事の本文が破綻していた:
  - 見出しが「速報/要点整理/引用」（＝`composeFactBody`の逐文リライト経路）になり、
  - 「パッチ26について情報が不足…リライトできません」等のLLM破綻文や、"14 Notes"・"000Z"・
    eスポーツ記事・Wikiリンク等の**ページ内ノイズの断片**が引用として並んでいた。
- 原因:
  1. `stripHtmlToText` がページ全体のテキスト（ナビ・見出しメタ・eスポーツ告知・関連記事・フッター・Wiki導線）を
     抽出し、実際のチャンピオン/アイテム変更がノイズに埋もれる。加えて `PATCH_NOTES_MAX_LENGTH`(15000字)で
     途中で切れ、変更本体が入りきらないことがある。
  2. その結果 `composePatchSummaryBody`（LLM要約）が要点を拾えず null を返し、**`composeFactBody`
     （ノイズ本文の逐文リライト）にフォールバック**して破綻文を量産していた。

## 含まれる機能

### F-E35-1: 取得テキスト量の拡大とノイズ低減（riot-datadragon.ts）
- `PATCH_NOTES_MAX_LENGTH` を拡大（例 15000→60000）。Haikuは200k文脈なので、パッチノート本体が
  入りきるようにする（LLM呼び出しは新パッチ時のみ＝月2回程度で低コスト）。
- `stripHtmlToText` のノイズ低減（best-effort・過剰にしない）:
  - `<nav>`/`<header>`/`<footer>`/`<aside>` 要素をタグ除去前に丸ごと落とす。
  - 明らかなボイラープレート行（極端に短い1〜2文字の断片の連続、重複するナビ語）を軽く間引く。
  - ※完全な本文抽出は難しいので、主眼は「本体が入りきる量」＋「後段プロンプトでノイズを無視させる」。

### F-E35-2: 要約プロンプトの強化（compose.ts の PATCH_SUMMARY_SYSTEM_PROMPT）
- 「渡すテキストは公式パッチノート**ページ全体のダンプ**で、ナビ・見出し・日付・eスポーツ告知・関連記事・
  Wiki導線などの**無関係なノイズを多く含む**。それらは無視し、**チャンピオン名や能力/ステータスの
  数値変更（強化・弱体・アイテム調整）だけ**を拾って要約すること」を明記。
- 「変更が明確に読み取れない場合のみ空配列。ノイズを変更点として拾わない（捏造禁止）」を維持・強調。
- 出力JSON形式は現状維持（extractJsonObjectで堅牢に解析済み）。

### F-E35-3: 失敗時のクリーンフォールバック（composeArticleBody）
- riot＋パッチノート本文（≥PATCH_NOTES_MIN_LENGTH）のとき `composePatchSummaryBody` が null（要約失敗）でも、
  **`composeFactBody`（ノイズ本文の逐文リライト）には落とさない**。代わりに**クリーンな簡易パッチ記事**を組む:
  - 見出し「パッチ<公式番号>の変更点」＋短い定型段落（例「パッチ<番号>が公開されました。主な変更点は
    公式パッチノートをご確認ください。」）＋出典（公式パッチノートURL）。逐文リライトやノイズ断片は入れない。
- 通常の汎用パッチitem（本文が無い＝短いcontent）の場合は従来どおり `composeFactBody`（生成物は問題ない）でよい。
  ※破綻していたのは「パッチノート本文（ノイズ込み）を composeFactBody に流した」ケースのみ。それを断つ。

## 制約・非目標
- **捏造禁止**（公式に書かれた変更のみ）。リーク/PBEは対象外。
- reddit/5ch/clip・タイトル生成・レス編集・NG・サムネ・ナビ削除には触れない。新規依存なし。
- mock既定（APIキー無し）ではパッチノート本文取得は走らず（fetchはlive時のみ）、従来の簡易パッチ記事のまま（回帰なし・コスト0）。
- LLM呼び出しはパッチ記事1本1回（新パッチ時のみ）。

## テスト（必須・実API/実ネット非依存）
1. `stripHtmlToText`: nav/header/footer/aside 要素が除去され、本文相当のテキストが残る。
2. `fetchPatchNotesText`: 上限が拡大され本体が入りきる（モックHTMLで確認）。取得失敗/短すぎで null は維持。
3. compose: パッチノート本文＋スタブLLMの要約 → まとめ体裁。要約が null（LLM空/例外/全カテゴリ空）のとき、
   **composeFactBodyの逐文リライトではなく**クリーンな簡易パッチ記事（見出し＋定型段落＋出典）になる。
4. 通常の汎用パッチitem（短いcontent）は従来どおり composeFactBody で問題ない出力（回帰なし）。
5. 既存の riot/パイプラインテストが回帰しない。

## 受け入れ基準
1. `npx vitest run` 全Green（新規/更新含む・実API/実ネット非依存）。
2. `npx tsc --noEmit`・`npm run build`・`npm run lint` 通過。
3. パッチノート本文が取れて要約成功時は「主な強化/弱体チャンピオン・アイテム」のまとめ記事。要約失敗時は
   クリーンな簡易記事（破綻文・ノイズ断片が出ない）。捏造なし。
4. mock既定は従来どおり（回帰なし・コスト0）。新規依存なし。

## 評価基準（evaluator向け）
- テストGreen・build/tsc/lint通過。実機(mock)でパッチ/メタ記事が従来どおり出る（回帰なし・コンソールエラー0）。
- スタブで「要約成功→まとめ」「要約失敗→クリーン簡易記事（composeFactBody非経由・破綻文なし）」を確認。
- 受け入れ基準1〜4を満たす。
