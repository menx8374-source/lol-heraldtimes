# Sprint 7 brief — 自動公開スケジューリングとエラー耐性・運営ログで完全自動運営を回す

> 仕様書 `docs/spec/lol-matome-sokuhou-spec.md` から Sprint 7 該当部分を原文のまま抜粋。generator/evaluator の主参照先。

## 対象プラットフォーム
`web`（自動運営のバックエンド／バッチ処理を含む）。

## ⚠ このスプリントの実装方針（全てモック）
このスプリントは Sprint 3〜6 の各工程を1本のパイプラインに統合する。**収集工程（Reddit／5ch／Riot）も記事・タイトル生成の LLM も、当面モック／スタブ実装**（ユーザー決定 2026-07-25: まず全スプリントをモックで通す）。いずれも差し替え可能な抽象（`SourceAdapter`／`LLMClient`）越しに呼ぶ。パイプライン統合テスト（完走・上限・重複防止・失敗継続）は決定論で Green にできる設計にする。**API キーは要求しない**。

## 含まれる機能: F10, F11

### F10. 自動公開・スケジューリング・継続運営
- 説明: 収集→重複排除→記事生成→タイトル生成→安全フィルタ→公開までの一連の流れを、定期スケジュール（例: 数時間おき）で人手なしに繰り返す。1回の実行で決めた本数を公開し、公開時刻を分散させる等、まとめサイトとして自然な更新頻度で回す。
- 優先度: Must
- 受け入れ基準:
  - [ ] スケジュール実行を1回起動すると、収集→重複排除→記事生成→タイトル生成→安全フィルタ→公開まで人手介入なしで完走し、新しい公開記事が0件より多く増える。
  - [ ] 1回の実行で公開する記事本数の上限を設定でき、その本数を超えて一度に公開しない。
  - [ ] スケジュール設定（実行間隔）を持ち、設定に従って繰り返し実行できる（少なくとも、繰り返し起動を模擬したときに毎回新規記事が積み上がる）。
  - [ ] 同じ実行を続けても既公開記事が重複公開されない（F6 の重複排除が公開段階でも効く）。
  - [ ] 記事化候補が枯渇しているときは、エラーにならず「今回は新規公開なし」で正常終了する。

### F11. エラー耐性・自動リカバリ・運営ログ
- 説明: 完全自動運営を止めないため、各工程の失敗を握りつぶさず記録しつつ、1件の失敗で全体を停止させない。失敗した工程は次回実行でリトライされ、実行結果（収集件数・生成件数・公開件数・失敗件数）がログに残る。
- 優先度: Must
- 受け入れ基準:
  - [ ] いずれかの収集ソース・生成・タイトル・フィルタのうち1件が失敗しても、パイプライン全体は停止せず、他の記事の処理を完走する。
  - [ ] 各実行ごとに、収集件数・記事化候補数・生成成功／失敗数・公開数・保留数を含む実行ログが記録される。
  - [ ] 生成やタイトル付けに失敗した候補は破棄されず、次回実行で再処理の対象になる（恒久的に消えない）。
  - [ ] 外部ソースがすべて応答しない最悪ケースでも、パイプラインはクラッシュせずログにエラーを残して正常終了する。

## このスプリントの受け入れ基準
- [ ] スケジュール実行を1回起動すると、収集→重複排除→記事生成→タイトル生成→安全フィルタ→公開まで人手介入なしで完走し、新しい公開記事が0件より多く増える。
- [ ] 1回の実行で公開する記事本数の上限を設定でき、その本数を超えて一度に公開しない。
- [ ] 実行間隔のスケジュール設定を持ち、繰り返し起動を模擬すると毎回新規記事が積み上がる。
- [ ] 同じ実行を繰り返しても既公開記事が重複公開されない。
- [ ] 記事化候補が枯渇しているとき、エラーにならず「今回は新規公開なし」で正常終了する。
- [ ] 収集・生成・タイトル・フィルタのいずれか1件を意図的に失敗させても、パイプライン全体は停止せず他記事の処理を完走する。
- [ ] 各実行ごとに、収集件数・記事化候補数・生成成功／失敗数・公開数・保留数を含む実行ログが記録される。
- [ ] 生成・タイトル付けに失敗した候補は破棄されず、次回実行で再処理対象になる。
- [ ] 全ソースが応答しない最悪ケースでもクラッシュせず、ログにエラーを残して正常終了する。

## 評価基準
- 致命的バグ: 0件
- コンソールエラー: 0件
- 上記受け入れ基準の充足率: 100%
- パイプライン統合（完走・上限・重複防止・失敗継続）の自動テストが Green
