# 横断学習メモリ（learnings）

**このファイルは案件をまたいで蓄積される教訓の常設メモリです。** 個々のプロジェクトの `docs/project-memory.md` が「その案件の中の記憶」であるのに対し、こちらは「次の新しい案件にも引き継ぎたい一般化された教訓」を溜める場所です。

- `planner` は新しい仕様を書く前にこのファイルの「## プロダクト設計の教訓」を読み、同じ轍を踏まないようにします。
- `architect` は技術ベースラインを決める前に「## 技術選定の教訓」を読み、既知の地雷を避けます。
- `generator` は実装前に「## 実装・運用の教訓」を読みます。
- `/retro` コマンド（およびオーケストレーターがスプリントを「要人手介入」で確定させたとき）が、根本原因を一般化してここに追記します。

## 追記のルール

- **一般化して書く。** 「このプロジェクトのボタンが動かなかった」ではなく「◯◯という構成では△△が起きやすい。□□で回避する」という、次案件で再利用できる粒度にする。
- 1エントリは**症状 → 原因 → 次への適用**の3点を簡潔に。プローズにしない。
- 特定案件の固有名詞・秘密情報は書かない（横断ファイルなので他案件からも読まれる）。
- 既に同じ教訓があれば新規追加せず、既存エントリを更新する（肥大化防止）。
- 教訓が**誤りだと分かった場合は削除する**（古い前提を残さない）。

## エントリの書式

```
### <短いタイトル>
- 症状: 何が起きたか（観測事実）
- 原因: なぜ起きたか（一般化した根本原因）
- 次への適用: 次案件でどう振る舞えば回避できるか（planner/architect/generator向けの具体的指示）
- 分類: product | tech | impl | ops
- 記録日: YYYY-MM-DD
```

## 実装・運用の教訓（generator向け）

### ローカル専用パイプラインでは品質ゲートのレビュースキルが自動起動できない
- 症状: `/security-review` が `git log ... origin/HEAD...` の基準解決に失敗（`unknown revision origin/HEAD`）。`/code-review` は当ハーネスで Skill ツールからのモデル起動が無効化されていて呼べない。
- 原因: `/security-review` は「リモート追跡ブランチ（`origin/HEAD`）」を差分基準にする前提。このパイプラインは no-push hook でローカルコミットのみ・リモート未設定のため、**初回だけでなく全スプリントで** `origin/HEAD` が存在しない。`/code-review` はユーザー起動専用コマンドで、オーケストレーターからの自動呼び出しは不可（ハーネス依存）。
- 次への適用: これはコード不備ではなくローカル専用運用のツール制約。**リトライ上限を消費させない。** 毎スプリント、オーケストレーターがステージ済み差分（`git diff --cached [HEAD]`）に対して手動でセキュリティ観点（XSS/SQLi/秘密混入/信頼境界の入力検証/認可）と正しさ観点を精査して代替する。`npm audit`（依存監査）・evaluatorの実機検証・テストGreen・`/simplify`（4観点サブエージェントfan-out）は通常どおり機能するので、それらと手動レビューを組み合わせて品質ゲートを満たす。
- 分類: ops
- 記録日: 2026-07-25

### i18n: 非ASCIIを含む動的URLセグメントは「エンコード済みURL」で検証する
- 症状: 日本語タグの一覧ページ（`/tags/[tag]`）が本番ブラウザ遷移で常に0件・見出しが生の `%E3%83%...`。自己確認では見逃し、evaluatorの実機操作でFAIL。
- 原因: ブラウザ／Next の `<Link>` は非ASCIIの動的セグメントをURLエンコードして遷移するため、ページが受け取る値はエンコード済み文字列。それを `decodeURIComponent` せずにDBクエリ・表示へ流すと、生の日本語で保存されたデータと一致せず0件になる。`curl` で生UTF-8パスを叩くと（curlはエンコードしないため）バグが再現せず見逃す。
- 次への適用: generatorは非ASCIIが載りうる動的セグメント（タグ・カテゴリ名・ユーザー名等）を受け取ったら必ず `decodeURIComponent`（例外を捕捉）してからクエリ・表示に使う。デコードを純関数化し、エンコード済み入力→元文字列の回帰テストを書く。自己確認・evaluator検証は**実際にエンコードされたURL**（またはブラウザ実クリック）で行い、生UTF-8パスの`curl`だけで済ませない。`searchParams` はNextが既にデコード済み・専用ASCIIスラッグ運用の箇所は対象外。
- 分類: impl
- 記録日: 2026-07-25

### 複数ファイルが同一の実DBに書き込むVitest結合テストはファイル並列実行でレースする
- 症状: DB結合テスト（Prisma+SQLite）を2ファイル目に追加した途端、`npm test`が数回に1回だけ失敗（片方のファイルの`deleteMany`が、並列実行中のもう片方のファイルのデータを消す）。1ファイル単独実行では常に成功するため原因特定に時間がかかりやすい。
- 原因: Vitestは既定でテストファイルを並列実行する。複数ファイルが同じ実体DB（テスト専用ファイルであっても）に対して無条件`deleteMany`等で共有状態を書き換えると、ファイル単位の実行順序・タイミングに依存した非決定的な失敗になる。
- 次への適用: DB結合テストが2ファイル目以降に増える時点で、`vitest.config.ts`に`test.fileParallelism: false`を設定しファイル単位を直列実行にする（テストDBファイルをテストごとに分離する手段より低コストで確実）。設定後は同じ全体テストを複数回連続実行し、決定的にGreenであることを確認してから完了とする。
- 分類: impl
- 記録日: 2026-07-25

### クライアント専用状態（localStorage等）由来のUIは useState遅延初期化+suppressHydrationWarning では反映されない
- 症状: localStorageに保存した「選択中」状態のハイライト（`aria-pressed`/背景色）が、リロード後に一切表示されない（フラッシュではなく恒久的に非表示）。しかも内部stateは復元されているため、未選択に見えるボタンを押すと逆の挙動（加算でなく取り消し）になる。既存のテーマ切替トグルは同じ書き方で問題なかったため見落としやすい。
- 原因: SSRはlocalStorageを読めず「未選択」でHTMLを描画する。クライアントで `useState(初期値=localStorage読み)` にしても、hydration時にReactはサーバー描画DOMを維持し、`suppressHydrationWarning` は不一致の警告を黙らせるだけでDOMを更新しない。マウント後に再レンダーを起こす契機が無いため、次のユーザー操作までハイライトが出ない。テーマトグルが成立するのは `<head>` のブロッキングno-flashスクリプトが描画前にクラスを付けDOMを一致させているからで、そのスクリプトが無い局所UIには同じ手が使えない。
- 次への適用: 「サーバーでは確定できずクライアントのlocalStorage等でのみ決まる表示状態」は **`useSyncExternalStore`（`getServerSnapshot`は常に未選択相当を返し、`getSnapshot`でlocalStorageを読む）** で実装する。書き込み時に購読者へ通知して再レンダーを起こす。代替として post-mount の `useEffect` でstateを設定して再レンダーさせる（外部ストア同期の正当用途）。`suppressHydrationWarning` でごまかさず実際にDOMを更新すること。検証は必ず「操作→リロード→ハイライトが復元される」まで実機で確認する。
- 分類: impl
- 記録日: 2026-07-25

### 推移的依存のHigh脆弱性は「本番影響の有無」で対応を分ける。overrides は互換性を検証してから
- 症状: (a) 新規 Next.js プロジェクトで `npm audit` が postcss / sharp（本番ランタイム依存）に High を報告。`npm audit fix --force` は Next 本体を大幅ダウングレード（破壊的）しようとする。(b) 開発中に新しいアドバイザリが公開され、eslint ツールチェーン（brace-expansion→minimatch→eslint-plugin群、いずれも devDependencies）に High が多数出る。
- 原因: 脆弱性はフレームワーク/ツールの推移的依存にあり、パッチ取り込みまで各アプリに出続ける。naive な audit fix はメジャーダウングレード/破壊的アップグレードを提案する。
- 次への適用:
  1. **まず本番影響を切り分ける**: 脆弱性が `dependencies`（本番バンドルに載る）か `devDependencies`（eslint/ビルド時のみ）かを見る。**devDependency のみ（eslint 等）なら本番の攻撃面はゼロ**なので、緊急でブロッカー扱いにせず、破壊的変更を伴う修正は見送って明示的に記録する（正攻法は該当ツールのメジャー更新で、スコープを分けて対応）。
  2. 本番ランタイム依存なら、破壊的ダウングレードを避け `package.json` の `overrides`（npm）でパッチ版に引き上げ、**`npm install` → ビルド・テスト・lint・再監査で無影響を必ず確認**してから確定する。
  3. **overrides で全インスタンスを1バージョンに強制する際は、非互換な複数メジャーが同居する依存に注意**。例: `brace-expansion` を `^5` に強制すると、`minimatch@3`（eslint が使用）の期待と食い違い `@eslint/config-array` が例外を投げて lint が壊れた。監査は0件になっても lint/build が壊れるなら override は取り消す（監査の緑より本体ツールの動作を優先）。
- 分類: ops
- 記録日: 2026-07-25
